## 1. Repository organization

**Single repo, structured by source-state attributes.** chezmoi encodes file metadata and rename rules directly into source filenames rather than in a separate manifest. The reference table defines each prefix: `dot_` "Rename to use a leading dot, e.g. `dot_foo` becomes `.foo`"; `private_` "Remove all group and world permissions from the target file or directory"; `readonly_` "Remove all write permissions"; `executable_` "Add executable permissions to the target file"; `empty_` "Ensure the file exists, even if is empty"; `create_` "Ensure that the file exists, and create it with contents if it does not"; `modify_` "Treat the contents as a script that modifies an existing file"; `encrypted_` "Encrypt the file in the source state"; `literal_` "Stop parsing prefix attributes." For directories the allowed prefixes are `remove_`, `external_`, `exact_`, `private_`, `readonly_`, and `dot_`. — https://www.chezmoi.io/reference/source-state-attributes/

`exact_` on a directory means chezmoi removes any target-directory entries that are not present in the source — use it only for directories you want to own completely, since it deletes unmanaged files that appear there. — https://www.chezmoi.io/reference/source-state-attributes/

**Scripts as source-state entries.** Scripts are ordinary source entries carrying the `run_` attribute, ordered and scoped by their prefixes: `once_` "Only run the script if its contents have not been run successfully before"; `onchange_` "Only run the script if its contents have not been run successfully before with the same filename"; `before_` "Run script before updating the destination"; `after_` "Run script after updating the destination." — https://www.chezmoi.io/reference/source-state-attributes/

**Special directories — pick the one matching the job.** chezmoi recognizes a small set of dot-prefixed special directories (all other dot-prefixed dirs are ignored):

- `.chezmoidata/` — "The files in `.chezmoidata/` directories are read in lexical order" (as `.chezmoidata.$FORMAT` or files within), providing static template data (TOML/YAML/JSON) available to every template. Use it for structured, non-secret config values shared across many files (theme names, package lists, path constants). — https://www.chezmoi.io/reference/special-directories/
- `.chezmoitemplates/` — "The files in `.chezmoitemplates/` are made available for use in source templates." Use it for reusable template fragments you `include`/`template` into multiple generated files, so a shared block is defined once. — https://www.chezmoi.io/reference/special-directories/
- `.chezmoiscripts/` — holds scripts that are "read, templated, and according to their phase attributes (`run_after_`, `run_before_`, etc.) and lexical ordering" — a place to keep `run_` scripts that should execute but never themselves be written to the target tree. — https://www.chezmoi.io/reference/special-directories/
- `.chezmoiexternal.$FORMAT` — declares external files/archives to pull in (read in lexical order), for vendored assets you don't want to commit. — https://www.chezmoi.io/reference/special-directories/

**When to use data vs templates:** `.chezmoidata` is for *values* (consumed by any template via `.varname`); `.chezmoitemplates` is for *reusable text/logic* (consumed via the template `include`/`template` action). Machine-varying values that should be *prompted* or *detected* belong in the config file / `.chezmoi.toml.tmpl` instead (see §2), not `.chezmoidata`, which is static and shared. — https://www.chezmoi.io/reference/special-directories/ and https://www.chezmoi.io/user-guide/manage-machine-to-machine-differences/

*Contested / opinionated:* single-repo-with-attributes (chezmoi) vs symlink-farm (GNU Stow) vs bare-git-repo is a genuine fork in the community, not a settled winner. GNU Stow is "a symlink farm manager which takes distinct sets of software and/or data located in separate directories … and makes them all appear to be installed in a single directory tree" and is explicitly "a structural management tool only — it does not handle templating, variable substitution, or secrets management." — https://www.gnu.org/software/stow/manual/stow.html. The bare-git-repo and installer-script approaches are catalogued as peer tutorials, not ranked — *[non-primary: a community link directory, not an authoritative spec]* https://dotfiles.github.io/tutorials/. Choose chezmoi's attribute model specifically when you need templating and secret injection, which the symlink approaches cannot provide.

## 2. Cross-platform strategy

**OS-conditional templating is the core mechanism.** "Variables populated by chezmoi are in `.chezmoi`, for example `.chezmoi.os`" and `.chezmoi.arch`. The documented pattern is a template conditional: `{{ if eq .chezmoi.os "darwin" }} # darwin {{ else if eq .chezmoi.os "linux" }} # linux {{ else }} # other operating system {{ end }}`. Text outside `{{ }}` actions "is copied literally," and `{{-` / `-}}` trim surrounding whitespace including newlines. — https://www.chezmoi.io/user-guide/templating/

**Share one file across OSes; branch only the differences.** chezmoi's stated primary goal is "to manage configuration files across multiple machines" via `text/template`. Coarse-grained per-machine inclusion/exclusion is handled by `.chezmoiignore`, which is "itself interpreted as a template" — e.g. ignore a `.work` file unless on the work host. — https://www.chezmoi.io/user-guide/manage-machine-to-machine-differences/

**Per-machine variables come from the config file, and can be prompted at init.** Machine-specific values live in `~/.config/chezmoi/chezmoi.$FORMAT` (TOML/YAML/JSON) under a `[data]` table and become template variables; run `chezmoi data` to list everything available. Values that must be captured on a fresh machine are collected by a `.chezmoi.toml.tmpl` that renders the config file at `chezmoi init`, using prompt functions (`promptString`, `promptBool`, etc.) — these are the machine-class questions ("is this a work machine?") whose answers then drive every downstream template. — https://www.chezmoi.io/user-guide/manage-machine-to-machine-differences/ and https://www.chezmoi.io/reference/commands/execute-template/ (which documents `--init` / `--promptString` for simulating them)

**One tool, different backends per OS — the mise case.** mise's own path defaults differ by platform: `MISE_DATA_DIR` is `~/.local/share/mise` (or `$XDG_DATA_HOME/mise`) on Linux/macOS but `%LOCALAPPDATA%\mise` (or `$XDG_DATA_HOME/mise`) on Windows, and this data dir is "not supposed to be shared across machines." — https://mise.jdx.dev/configuration.html. The *activation model itself* differs by OS: `mise activate` "updates your `PATH` and environment every time your prompt runs" and is "Recommended for interactive shells," whereas shims are "symlinks that intercept commands … Better for CI/CD, IDEs, and scripts," and critically "shims don't support all features of mise activate." — https://mise.jdx.dev/getting-started.html. On native Windows specifically: "While mise runs great in WSL, native Windows is also supported, though via the use of shims until someone adds powershell support," and "As you'll need to use shims, this means you won't have environment variables from mise.toml unless you run mise via mise x or mise run." — https://mise.jdx.dev/faq.html. So a cross-platform dotfiles repo must template the mise integration: `mise activate` on zsh/Unix, and a shims-first strategy (or explicit `mise activate pwsh` where it works) on Windows. TOML paths on Windows must use literal strings (`{ path = 'C:\tools\node' }`) because backslashes escape in double-quoted strings. — https://mise.jdx.dev/configuration.html

*Settled vs opinionated:* that OS branching belongs in templates (not forked files) is settled chezmoi guidance; whether to prompt at init vs hardcode host allowlists is a project choice chezmoi supports both ways (this repo does both — see §"how this repo aligns").

## 3. Secret management

**Keep secrets out of the repo; inject at apply time.** chezmoi's recommended approach is to retrieve secrets from a password manager during templating rather than committing them. Its 1Password integration exposes template functions that run the `op` CLI at apply time: `onepasswordRead` "Exposes `op read` command output as a template function," e.g. `{{ onepasswordRead "op://app-prod/db/password" }}`; `onepassword` retrieves structured JSON from `op item get $UUID --format json`; `onepasswordDetailsFields` lets "fields to be queried by key" rather than index. The `op` CLI must be installed and signed in (biometric unlock removes the manual `op signin` step), and `connect`/`service` account modes exist for headless/CI use. — https://www.chezmoi.io/user-guide/password-managers/1password/

**The `op://vault/item/field` reference is the unit of indirection.** The secret reference URI (e.g. `op://app-prod/db/password`) names a vault, item, and field so the config stores only a *pointer*, never the secret; `op read` resolves one reference and `op inject` substitutes references embedded in a file. — grounded in the chezmoi 1Password page's `op read "op://app-prod/db/password"` example, https://www.chezmoi.io/user-guide/password-managers/1password/. *[Canonical source flagged as unreachable: the authoritative 1Password developer docs at `https://developer.1password.com/docs/cli/secret-reference-syntax/` 301-redirect to `www.1password.dev`, which refused connection from the research environment on 2026-09-02 — the op:// shape above is corroborated by chezmoi's docs but was not verified against 1Password's own page.]*

**Encryption is the alternative when a value must be committed.** chezmoi "supports age, git-crypt, gpg, and transcrypt." A file added with `chezmoi add --encrypt` is stored "in ASCII-armored format in the source directory with the `encrypted_` attribute," and `chezmoi edit` "will transparently decrypt the file before editing and re-encrypt it afterwards." — https://www.chezmoi.io/user-guide/encryption/. Use encryption for secrets with no password-manager entry (a committed-but-encrypted keyfile); prefer live injection (§ above) for anything a manager already holds, so the secret never rests in the repo at all.

**The `.env.example` + gitignored `.env` pattern.** This convention — commit a `.env.example` template with placeholder keys, gitignore the real `.env` — is standard hygiene rather than a chezmoi feature, and Drew's own guardrails encode it ("keep `.env` gitignored with a committed `.env.example`"). It pairs naturally with chezmoi: generate the real `.env` from a template that pulls values via `onepasswordRead`, and keep `.env.example` as the committed shape. *[No single primary spec owns this pattern; it is settled community/tooling convention. The dotfiles community tutorial index does not even address secret-avoidance — https://dotfiles.github.io/tutorials/ — so treat "don't commit secrets" as an external assumption, not something that page teaches.]*

**The real risk: templates render secrets to plaintext on disk.** Any template function that injects a credential writes the *resolved plaintext* into the target file at `chezmoi apply` time — the protection is that the *source* stays clean, not that the *target* is encrypted. So the rendered file must land with restrictive permissions (`private_` → mode 0600) and outside the repo. chezmoi's docs describe the injection mechanism but, on the pages fetched, do **not** carry an explicit warning about plaintext-on-disk exposure — https://www.chezmoi.io/user-guide/encryption/ and https://www.chezmoi.io/user-guide/templating/ both omit it — so this is a reasoned consequence of the injection model, worth stating loudly rather than a quoted rule.

## 4. Modularity and shell startup

**zsh startup files, by scope (the primary contract).** From the zsh manual's STARTUP/SHUTDOWN FILES: `.zshenv` is "Read for all shells" (login, interactive, and non-interactive/scripts alike) — "Commands are then read from `$ZDOTDIR/.zshenv`"; `.zprofile` is login-shells-only ("If the shell is a login shell, commands are read from … `$ZDOTDIR/.zprofile`"); `.zshrc` is interactive-shells-only ("if the shell is interactive, commands are read from … `$ZDOTDIR/.zshrc`"); `.zlogin` is login-shells-only, read last; `.zlogout` runs on login-shell exit. — https://zsh.sourceforge.io/Doc/Release/Files.html. The practical rule that falls out: environment variables and `PATH` that non-interactive tools need go in `.zshenv`; interactive-only setup (prompt, keybindings, completions, aliases) goes in `.zshrc`; login-shell one-offs go in `.zprofile`/`.zlogin`. Startup files stop loading if `RCS`/`GLOBAL_RCS` are unset "at any point." — https://zsh.sourceforge.io/Doc/Release/Files.html

**PowerShell's profile equivalents.** "A PowerShell profile is a script that runs when PowerShell starts." Four profiles exist, executed in order — AllUsersAllHosts, AllUsersCurrentHost, CurrentUserAllHosts, CurrentUserCurrentHost — and "The **CurrentUserCurrentHost** profile always runs last … the profile most often referred to as *your PowerShell profile*." Cross-host setup belongs in `CurrentUserAllHosts`; host-specific setup (e.g. VS Code's `Microsoft.VSCode_profile.ps1`) in a host profile. `$PROFILE` holds the CurrentUserCurrentHost path, with the others as note properties (`$PROFILE.CurrentUserAllHosts`, etc.). Profiles don't run in remote sessions, and the **Restricted** execution policy blocks them entirely. — https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_profiles. PowerShell has no built-in `zshenv`-style "all invocations" file — a non-interactive `pwsh -c` still runs the profile unless `-NoProfile` is passed — so the zsh split between "all shells" and "interactive only" has no exact pwsh analogue; the closest lever is `-NoProfile` for scripts.

**Splitting a profile into ordered, error-isolated fragments.** Both a `shell.d`-style zsh loader and a `profile.d`-style pwsh loader are the same pattern: a thin loader enumerates numbered fragment files in sorted order and sources each. This repo already has companion research on the pwsh side — see `docs/pwsh-modular-profile.md` (the `profile.d` loader with per-module `try/catch` isolation and deterministic sort) and `docs/pwsh-lazy-load-tool-inits.md` (deferring tool inits behind first use). The key correctness point from that work, grounded in PowerShell's own docs, is that a bare `source`/dot-source loop has **no error isolation** — one fragment that throws aborts the rest — so the loader should wrap each fragment. That guidance and its citations live in those two notes and are not repeated here.

*Opinionated:* numbered-prefix ordering (`000-`, `010-`) is a widespread convention (mirrors `/etc/profile.d`, systemd drop-ins) but not mandated by any shell spec — it's a project choice for deterministic, insertable ordering. Keeping startup fast (deferring/​lazy-loading tool inits) is likewise a performance tactic, strongest on Windows where each spawn pays process-creation + AV-scan cost, and is contested only in how far to take it.

## 5. Bootstrapping, idempotency, testing

**One-command bootstrap.** The binary installs with `sh -c "$(curl -fsLS https://get.chezmoi.io)"`, and a fresh machine can install-init-apply in a single line: `sh -c "$(curl -fsLS https://get.chezmoi.io)" -- init --apply $GITHUB_USERNAME` (or, for a private SSH repo, `… -- init --apply git@github.com:$GITHUB_USERNAME/dotfiles.git`). — https://www.chezmoi.io/install/. Equivalently, once chezmoi is present: "chezmoi init --apply --verbose https://github.com/$GITHUB_USERNAME/dotfiles.git" combines init, checkout, and apply. — https://www.chezmoi.io/user-guide/setup/

**Idempotency is required, not optional.** "All scripts should be idempotent, including `run_onchange_` and `run_once_` scripts." `run_once_` scripts "execute once for each unique version of the content" (chezmoi tracks the content's SHA256 hash in a database); `run_onchange_` scripts "are only executed if their content has changed since the last time they were run successfully." Order with `before_`/`after_`: "To run scripts before or after the updates, use the `before_` or `after_` attributes." — https://www.chezmoi.io/user-guide/use-scripts-to-perform-actions/

**The hash-in-a-comment trigger.** To make a `run_onchange_` script re-fire when a *referenced* file changes, embed that file's hash in a comment: doing so means "the contents of the script will change whenever the contents of [the referenced file] are changed, so chezmoi will re-run the script whenever the contents of [that file] change." — https://www.chezmoi.io/user-guide/use-scripts-to-perform-actions/

**Verify before it lands.** `chezmoi diff` lets you "see what would change, without actually applying the changes"; "chezmoi will not make any changes to the actual dotfile until you run `chezmoi apply`." The safe daily loop is `chezmoi git pull -- --autostash --rebase && chezmoi diff`, then apply only "If you're happy with the changes." — https://www.chezmoi.io/user-guide/daily-operations/. For templates specifically, `chezmoi execute-template` exists "for testing templates or for calling chezmoi from other scripts," and with `-i`/`--init` it will "Include simulated functions only available during `chezmoi init`" so prompt-driven configs can be dry-run: `chezmoi execute-template --init --promptString email=me@home.org < ~/.local/share/chezmoi/.chezmoi.toml.tmpl`. — https://www.chezmoi.io/reference/commands/execute-template/

**Safe rollout so a broken template can't lock you out.** The diff-before-apply discipline above is the primary guard. Because `.zshenv` is read by *every* zsh (§4), a template error there breaks even `zsh -c`, so it is the highest-blast-radius file to validate with `execute-template`/`diff` before applying. — https://zsh.sourceforge.io/Doc/Release/Files.html and https://www.chezmoi.io/user-guide/daily-operations/. CI linting (running `chezmoi execute-template`/`chezmoi apply --dry-run` against the source in a workflow) is a project-level practice chezmoi enables but does not itself prescribe — treat it as sound engineering, not a quoted rule.

## 6. Common pitfalls / anti-patterns

- **Monolithic rc/profile files.** A single large profile has no failure isolation — one throwing section aborts everything after it. The fix is the ordered-fragment loader with per-fragment error handling (§4), documented for the pwsh side in `docs/pwsh-modular-profile.md`. *Settled* that isolation matters; *opinionated* how granular the split should be.
- **Committing machine-specific absolute paths.** These break on the next host and are exactly what templating + config data exist to eliminate — branch on `.chezmoi.os`/config vars instead of hardcoding `/opt/homebrew` or `%LOCALAPPDATA%`. — https://www.chezmoi.io/user-guide/manage-machine-to-machine-differences/. Note mise's data dir is explicitly "not supposed to be shared across machines" — https://mise.jdx.dev/configuration.html — so never commit a resolved mise path.
- **Over-templating.** Every `{{ }}` is logic that must be maintained and can fail at apply time in the highest-blast-radius files; prefer plain files where nothing varies and reserve templates for genuine per-machine difference. This is a *reasoned* caution (chezmoi encourages templates but every conditional is a place a broken render can lock you out — §5), not a quoted rule.
- **Secret leakage in PUBLIC dotfiles repos.** The whole point of `onepasswordRead`/`encrypted_` is that the committed source never contains a plaintext secret. — https://www.chezmoi.io/user-guide/password-managers/1password/ and https://www.chezmoi.io/user-guide/encryption/. The subtler leak is non-secret-but-identifying detail (internal hostnames, work repo/branch names) surfacing in a *public* dotfiles repo as motivating examples — a documented real incident in this very repo's environment; scrub before committing.
- **Tool-init spawn cost at every shell start.** Eagerly running many `tool init | source` calls pays process-creation (and, on Windows, AV-scan) cost on every prompt; defer inits behind first use where possible. — grounded in mise's activate-vs-shims tradeoff, https://mise.jdx.dev/getting-started.html, and detailed for pwsh in `docs/pwsh-lazy-load-tool-inits.md`. *Opinionated:* how aggressively to lazy-load is a taste/perf tradeoff, not settled doctrine.

## How this repo already aligns / where it could improve

Mapped to concrete files under this repo's `home/`.

### Already aligned

- **Source-state attributes used idiomatically (§1).** `dot_zshenv.tmpl`, `private_015-vault.sh.tmpl` (mode 0600 for rendered credentials), `exact_dot_oh-my-zsh/`, `executable_dot_git-azdo-helper.sh`, `empty_dot_hushlogin` — the filename-attribute model is applied correctly, including `private_` on the secret-bearing fragment.
- **All four special directories in use (§1).** `.chezmoidata/` (static values: `constants.toml`, `winget.toml`, `scoop.toml`, `skills.yaml`), `.chezmoitemplates/` (reusable fragments: `windows-relocation`, `path-functions`, `tool-functions`), `.chezmoiscripts/` (phase/OS-split `run_` scripts under `common/`, `darwin/`, `linux/`, `windows/`), and `.chezmoiexternal.toml.tmpl`. Data-vs-template-vs-config separation matches §1's guidance.
- **OS-conditional templating and per-machine prompts (§2).** `dot_zshenv.tmpl` branches on `{{ eq .chezmoi.os "darwin" }}`; `.chezmoi.toml.tmpl` uses `promptBoolOnce` for `ephemeral`/`personal` and a host allowlist to derive `$opVault` — i.e. it does *both* the detect-by-hostname and prompt-at-init strategies §2 describes.
- **mise's per-OS backend handled (§2).** `dot_config/shell/010-mise.sh.tmpl` runs `mise activate zsh` for interactive Unix shells; `dot_zshenv.tmpl` puts `…/shims` on PATH for non-interactive shells (topgrade, `zsh -c`) that never source `.zshrc` — exactly the activate-vs-shims split mise documents, and the Windows profile uses `mise activate pwsh` with a shims-first PATH heal.
- **Secrets injected, never committed (§3).** `private_015-vault.sh.tmpl` renders `GITHUB_TOKEN`/`GEMINI_API_KEY`/`CONTEXT7_API_KEY` via `onepasswordRead (printf "op://%s/…/token" .opVault)` at apply time into a mode-0600 file, with `.opVault` selecting Private vs Employee — a clean application of §3, including the "resolve at build time so shell startup needs no op session" note.
- **zsh startup scoping is correct (§4).** Env/`PATH` live in `dot_zshenv.tmpl` (all shells); interactive setup and the `source shell-loader.sh` call live in `dot_zshrc.tmpl`; the macOS `path_helper` reorder is countered in `dot_zprofile.tmpl` by re-sourcing `.zshenv` — a textbook use of the login-shell file.
- **Idempotent, hash-triggered scripts (§5).** `run_onchange_after_10-install-mise-tools.sh.tmpl` embeds `{{ include "…/mise/config.toml.tmpl" | sha256sum }}` in a comment so it re-fires only when the tool set changes — precisely the §5 pattern — and guards installs with `command -v` checks.

### Where it could improve

- **The pwsh profile is still the 238-line monolith (§4, §6).** `Documents/PowerShell/Microsoft.PowerShell_profile.ps1.tmpl` inlines ~8 tool inits with only spot `try/catch` (PSReadLine, oh-my-posh), so a throw mid-file still aborts later inits. The remedy is already designed in `docs/pwsh-modular-profile.md` (a `profile.d` loader with per-fragment isolation) — this note's §4 is the "why", that note is the "how". Converting it is the single biggest structural gap versus the zsh side.
- **The zsh loader has no per-fragment error isolation (§4).** `dot_config/shell-loader.sh.tmpl` does a bare `source "$config_file"` in a loop — a hard error in one fragment can abort the rest, the same failure mode called out for pwsh. Wrapping each source (subshell or trap) would bring it up to the isolation standard the pwsh redesign targets.
- **`.env.example` pattern not evidenced (§3).** Secrets flow through `onepasswordRead`, which is stronger than `.env` files, so this may be intentional — but if any tool in the repo consumes a `.env`, confirm a committed `.env.example` shape exists per Drew's guardrail. No `.env.example` was observed at the paths inspected; flag rather than assume.
- **Public-repo disclosure surface (§6).** This repo is public, and it encodes work-machine relocation logic (`windows-relocation`) and host allowlists. Machine hostnames and a vault name are already published in tracked source (`home/.chezmoi.toml.tmpl`), so the "publish the mechanism, not the evidence" discipline is not a pre-push gate here — it is a scrub decision on content that is already live, plus a standing rule for every future commit. Identifiers are deliberately not repeated in this note; read them from the file.
